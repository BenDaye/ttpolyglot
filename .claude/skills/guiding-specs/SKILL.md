# 规格文档创建框架

## 概述

将提案拆分为可执行的 Spec（需求规格 + 技术设计 + 任务分解），通过两阶段访谈完成。

## Spec 类型

| 级别 | 含义 | 示例 |
|------|------|------|
| `story` | 用户故事 | 用户可以批量导入翻译文件 |
| `task` | 技术任务 | 添加 YAML 导出支持 |
| `bug` | 缺陷修复 | 修复翻译键重复检测 |
| `spike` | 技术调研 | WebSocket 实时协作方案调研 |

## 命名规则

格式: `{level}-{feature-name}`
示例: `story-batch-import`、`task-yaml-export`、`bug-duplicate-key`、`spike-websocket`

## 目录结构

```
.spec-workflow/specs/active/{level}-{feature-name}/
├── requirements.md    # 需求文档
├── design.md          # 技术设计
└── tasks.md           # 任务分解
```

## 阶段 1: 需求定义（产品视角）

### 访谈流程（3 轮）

**第 1 轮：核心需求**
1. 功能描述（一句话）？
2. 用户场景（作为...我想要...以便...）？
3. 核心交互流程？

**第 2 轮：细节与边界**
1. 正常流程的步骤？
2. 异常场景和错误处理？
3. 与现有功能的关联？
4. 数据模型需求？

**第 3 轮：验收标准**
1. 功能验收条件？
2. 性能要求？
3. 兼容性要求（Web/桌面/移动端）？

### 输出: requirements.md

```markdown
# {功能名称}

## 状态
- 状态: 草稿 → 已批准
- 类型: {story|task|bug|spike}
- 范围: {涉及的包}
- 创建日期: {YYYY-MM-DD}
- 关联提案: {链接，如有}

## 用户故事
作为 {角色}，我想要 {功能}，以便 {价值}。

## 背景
{问题描述和上下文}

## 需求详情

### 功能需求
1. {需求 1}
2. {需求 2}

### 非功能需求
- 性能: {要求}
- 兼容性: {平台}

## 验收标准
- [ ] {标准 1}
- [ ] {标准 2}

## 约束
{已知技术限制或依赖}
```

## 阶段 2: 技术设计（开发视角）

### 前置条件

requirements.md 的状态为「已批准」

### 访谈流程（2 轮）

**第 1 轮：方案设计**
1. 使用 Serena 分析现有代码结构
2. 确定整体实现方案
3. 识别需要新增和修改的文件
4. 确定数据库迁移需求
5. 确定 API 接口设计

**第 2 轮：细节确认**
1. 前后端接口契约
2. 错误处理策略
3. 测试策略
4. 任务执行顺序

### 输出: design.md + tasks.md

（见 `/spec:design` 命令的模板）

## Story Point 估算

| SP | 时间参考 | 复杂度 | 示例 |
|----|----------|--------|------|
| 1 | < 2 小时 | 单文件简单修改 | 添加一个字段 |
| 2 | 2-4 小时 | 单包小功能 | 新增一个 API 端点 |
| 3 | 4-8 小时 | 跨文件中等功能 | CRUD 完整流程 |
| 5 | 1-2 天 | 跨包功能 | 新增完整 feature 模块 |
| 8 | 2-3 天 | 多包复杂功能 | 涉及 model + server + app |

### SP > 5 拆分策略

如果单个 Spec 总 SP > 8，考虑拆分：
1. 按前后端拆分（server Spec + app Spec）
2. 按功能阶段拆分（基础功能 + 高级功能）
3. 按数据层拆分（model + service + UI）

## 状态流转

```
草稿 → 已批准 → 进行中 → 已完成 → 已归档
             → 已拒绝
```

## 命令参考

| 命令 | 用途 |
|------|------|
| `/spec:create` | 创建新 Spec（需求访谈） |
| `/spec:design` | 为已批准的 Spec 创建技术设计 |
| `/spec:check` | 检查 Spec 实现进度 |
